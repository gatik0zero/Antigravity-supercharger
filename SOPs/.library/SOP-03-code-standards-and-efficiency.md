# SOP 03: Code Standards and Efficiency

## 1. Objective
To maintain high readability, maintainability, and operational efficiency across all generated code. The AI agent must act as an expert, efficiency-focused development partner, prioritizing lean, working solutions over theoretical fluff.

## 2. Scope
This SOP applies to all programming languages, scripts, and documentation generated by the AI within the Antigravity IDE.

## 3. Directives

### 3.1. Coding Standards
- **Naming**: 
  - Variables/functions: `camelCase`
  - Classes/components: `PascalCase`
  - Files: `kebab-case`
  - Constants: `SCREAMING_SNAKE_CASE`
- **Structure**: One component/class per file. Keep functions small and focused (max 50 lines). Keep files under 300 lines (split if longer).
- **Code Quality**: No `any` types in TypeScript. No magic numbers (use constants). No deeply nested callbacks (use async/await). Remove dead code; do not comment it out. No `console.log` in production.
- **Documentation**: JSDoc for exported functions. Inline comments for WHY, not WHAT. Never document obvious code.

### 3.2. Efficiency & Work Style (Global Rule)
- **Lean & Efficient**: No fluff, no filler. Lead with the solution, explain after. Keep explanations under 3 sentences unless requested.
- **Correct First, Fast Second**: Never sacrifice correctness for speed. Verify logic before outputting.
- **Do the Work**: Execute all steps of a task. Do not stop after step 1. If fixing a bug, proactively fix related issues.
- **Fail Fast**: If something won't work, state it immediately and propose an alternative.

### 3.3. Web Development specifics
- **HTML**: Use semantic HTML5 elements. One `<h1>` per page. Include `alt` tags and `lang` attributes.
- **CSS**: Mobile-first responsive design. Use CSS custom properties. Avoid `!important`.
- **Performance**: Compress images (WebP). Defer non-critical JS. Target < 3s initial load time.
- **A11y & SEO**: Ensure keyboard accessibility. Provide proper meta tags and schema markup.

### 3.4. Claude Champion Practices
- When documenting or explaining a solution, provide the actual prompt or the runnable code snippet rather than just pointing to docs.
- Use `Plan mode` (conceptually) by outlining what files will be touched before making massive, destructive edits.

## 4. Situational Triggers
- **Trigger**: The user asks a question about how to implement a feature.
- **Action**: Provide the direct, working code snippet first. Follow with a max 3-sentence explanation. Use bullet points for lists.
- **Trigger**: Editing a massive file.
- **Action**: Read the file using `view_file` first. Group related edits in one pass using `multi_replace_file_content`. Avoid multiple sequential passes if possible.
